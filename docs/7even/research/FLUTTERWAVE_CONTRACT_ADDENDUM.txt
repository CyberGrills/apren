7EVEN FLUTTERWAVE PAYMENT CONTRACTS
16 October 2026. Read-only architecture revision. User correction supersedes the earlier manual-payment proposal: customers pay THROUGH 7even checkout using Flutterwave; provider split settlement sends the merchant's share to its bank; 7even's commission is 10%. Track the full payment and transaction lifecycle. No credentials, provider API calls, provisioning or application edits were performed.

Proposed provider contract
Use Flutterwave Standard v3 hosted checkout, initialized server-side at POST /v3/payments, with the approved merchant subaccount bound by server state. Store explicit provider API version, environment, account identity and webhook-verification mode. Never accept a customer-supplied beneficiary, amount, commission or merchant ID as authority. The redirect is a status prompt only. Provider verification, not staff confirmation, establishes paid status. Reception remains the trusted source of actual service fulfillment.

One booking contains a quote snapshot, one or more immutable payment attempts, actual provider transactions, allocations, financial journal records, refund records and settlement observations. These have separate states. A successful payment is not proof of merchant-bank settlement, service completion or completed refund. The earlier phrase '7even does not process payments' must be removed. There is no need to introduce a stored-value customer cash wallet.

Checkout initialization and uncertainty
1. In one local transaction, authenticate/authorize the customer, validate the immutable quote and eligible merchant/subaccount, place/verify a live capacity hold, persist an attempt with unique tx_ref, exact NGN amount, commission/split/policy snapshot, request payload hash and request-scoped idempotency key. Persist the initialization job/outbox intent with it.
2. Call the provider outside the database transaction. Record initialization success and link, definitive rejection or UNKNOWN_AFTER_TIMEOUT. A client retry returns the existing attempt; it does not generate a new reference. Do not hold database locks while waiting for the provider.
3. If a response is lost, reconcile using the existing reference/attempt and provider APIs before retrying a possibly effective request. Do not assume v3 Standard supports a generic provider idempotency header that has not been documented/tested for this endpoint. Bounded retries, lease expiry, next-attempt time and a review path are explicit. A local unique key alone cannot provide distributed exactly-once execution.
4. A definitively failed/cancelled attempt may be replaced under a fresh reference. Multiple successful transactions for one reservation are separate financial facts. Allocate the booking once, journal each actual receipt once and put excess/duplicate charges into refund review rather than silently dropping the second payment.
5. Align the hosted-session expiry with the hold and attempt to disable known links after cancellation/expiry. Neither mechanism can eliminate delayed bank/webhook races; expired paid transactions still require reconciliation.

Webhook authentication, ingestion and verification
Pin one contract; reject missing/malformed/mismatched authentication. Current official /docs/webhooks (the v3 route redirects here) documents verif-hash equal to a configured secret, compared in constant time. /v4.0/docs/webhooks specifies base64 HMAC-SHA256 of the exact raw payload in flutterwave-signature. The v4 page also contains contradictory old examples. Do not mix its status/schema/authentication semantics with v3, and never fall back from failed HMAC to static-secret comparison. A protocol change is an explicit, tested configuration change, not automatic header detection.

After authentication and bounded schema validation, durably store a redacted necessary event/inbox record and work item before acknowledging HTTP 200. If durable ingestion fails, do not acknowledge success. Network verification and effects run asynchronously. Replays return successful acknowledgments without duplicate effects. Use the provider's stable event identity where present; v3 events cannot be assumed to have a separate event UUID. Raw-payload hashes can identify identical deliveries, but financial uniqueness is enforced on provider environment/account/transaction ID plus effect kind and refund/settlement identity. Do not discard a later legitimate state observation merely because a transaction ID was seen before.

For any purported payment success, call GET /v3/transactions/{id}/verify (or the documented reference lookup during recovery). Check successful status, exact expected tx_ref, NGN currency, expected amount and server-owned attempt/account association. Compare exact decimal values after lossless conversion to kobo. Wrong reference/currency/underpayment is review, never value. For the starter policy, overpayment is also review until an approved excess-refund policy exists. Do not use charged_amount, app_fee or a browser value interchangeably with the quoted amount. Store provider-observed fees and discrepancies separately. Ignore stale failed notifications that contradict verified success; refunds/disputes are explicit later events rather than reversal of historical receipt.

Payment-to-capacity transition
Lock the attempt/reservation and affected allocations in consistent order. Record provider-confirmed receipt and its journal once. If the hold is still live at server commit and the reservation remains eligible, convert it to confirmed allocation atomically. If expired, cancelled, already fulfilled elsewhere or mismatched, mark PAID_REVIEW_REQUIRED without reviving the hold or inventing inventory. Provider paid_at or webhook timestamps cannot override current capacity authority. Rebooking requires a fresh availability check and an explicit resolution; refund remains pending until provider confirmation. A delayed verification can therefore produce 'payment received, booking needs review' truthfully.

10% commission and splits
Persist commissionRateBps=1000 and an immutable commission basis and rounding rule. Compute kobo with integer/decimal arithmetic, then format the provider's major-unit decimal exactly. Quote, charge request, verified transaction and financial journal must agree. The merchant does not necessarily receive 90% after provider fees, taxes or other deductions. The fee bearer, commission basis (gross total versus eligible service subtotal), refund/commission policy and rounding are approval-level settings, not hidden defaults.

Prefer an explicit per-transaction split over ambiguous subaccount defaults. The v3 split guide's override examples identify transaction_charge_type='flat' as platform flat commission, with the merchant receiving the remainder after fees. An exact locally calculated commission may use that contract after sandbox proof, including odd-kobo values. The guide contains contradictory default split descriptions, so '0.10 means 10% for us' is insufficient evidence without verifying actual provider allocation. Do not send a separate bank transfer when Flutterwave is already settling the split.

Merchant onboarding and beneficiary changes
Collect only required merchant/bank information, verify bank/account mapping and business authorization, create/retrieve the provider subaccount server-side, and persist the confirmed ID bound to that tenant/environment. Subaccount creation alone does not establish legal ownership or completed merchant vetting. Payment publication requires an approved enabled beneficiary. Scope and audit beneficiary changes, reverify them, and preserve the old binding on existing payment attempts. A suspended/missing/revoked beneficiary blocks new checkout. Flutterwave's split documentation assigns marketplace responsibility for merchant vetting and disputes to the platform; bank settlement does not remove that obligation.

Financial journal, settlement and refunds
Use immutable balanced double-entry postings per currency, expressed in integer kobo; point postings balance separately in their own unit. Post only facts/explicit obligations, with event IDs, provider references, merchant, actor and original-entry links. Derived balances are reconciled views. No fee, reversal or journal correction edits an earlier posting. Example control flow: a verified gross receipt balances provider receivable against merchant payable and platform commission/deferred commission; actual fees allocate to their approved bearer; provider settlement clears the relevant payable/receivable; platform bank receipt has its own observed/in-transit state. Final account classification/revenue recognition requires qualified review, particularly commission before fulfillment.

Payment, settlement, refund and dispute each have pending/success/failed/uncertain states. Reconcile provider charge detail, settlement batches, fees and actual bank/report evidence; do not label settlement complete merely because charge verification returns successful. Persist mismatches for investigation. A refund request is authorized, bounded by captured amount less previously completed/reserved refunds, durably identified and serialized against concurrent refund requests. Send it once; on timeout query the existing refund before retrying. Record accepted/processing/completed/failed/unknown separately. Provider acceptance does not mean customer receipt. A settled split may require merchant recovery/platform funding under the approved policy; do not assume the refund API automatically claws money back from every beneficiary. Commission, merchant share and points adjustments use compensation records tied to the original transaction.

Acceptance criteria before a real-money readiness claim
- Sandbox hosted checkout -> authenticated webhook -> independent verification -> atomic reservation confirmation -> reception fulfillment -> points once, visible in customer/business/admin histories.
- Repeat initialization, callback and webhook 10 times; only one intended attempt/allocation/reward. Separate actual duplicate charges are retained and reviewed, not ignored.
- Forged/missing headers, v4 raw-body mutation, wrong-version headers, replayed events, malformed bodies, wrong amount/currency/reference/account, partial/overpayment, delayed and reordered events produce no unauthorized booking or money effect.
- Race 20 customers for the final unit, payment verification against expiry/cancellation, and walk-in against web booking. Assert allocation counts and final ledger, not HTTP status alone.
- Crash before/after provider call, inbox commit, journal commit and acknowledgment; timeout after a possible charge; restart; provider outage and missing webhook. Recovery reaches provider/local agreement or explicit unresolved review without blind charges.
- Prove exact 10% and fee-bearer outcomes across tiny/odd-kobo/large amounts using actual sandbox split/settlement evidence. Verify approved merchant account mapping; attempts retain their beneficiary snapshot through a later account change.
- Full/partial refund, duplicate/concurrent refund, refund after settlement, refund timeout, failed refund and disputed charge reconcile with provider facts and balanced postings. A pending refund is never shown as completed.
- Relevant dependency/secret/static/API scans, provider sandbox tests, backup/recovery and reconciliation checks, monitoring/abnormal-payment alerts, current applicable payment/privacy/PCI obligations and qualified review remain production release requirements. No live credentials or real funds are needed for this architecture task.
