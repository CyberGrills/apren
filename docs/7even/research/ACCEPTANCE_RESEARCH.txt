CURRENT TEST/BUILD/SETUP DEFICIENCIES

Root npm workspaces and React/Vite/Node/Express/pg are real patterns worth retaining where they fit. The root install lifecycle calls npm install recursively. Root build only builds apps/web. Identity/wallet test scripts deliberately exit 1 with no-test placeholders; the remaining packages have no meaningful tracked automated tests. No canonical schema migrations, test bootstrap, complete environment example or full PostgreSQL setup is supplied. The previous Vite build and node/bash syntax checks passed but browser screens still crashed, demonstrating their limited coverage. The existing start:all launches eight processes but omits notifications. Notification has no workspace manifest or persistence. Active browser requests target localhost ports; the gateway routes some features to obsolete services. PG* and POSTGRES_* configure independent DB clients. Overlapping server routes and historical generators are not a suitable framework to extend.

SEVEN ROOT CAUSES AND REQUIRED REPLACEMENT PROPERTIES

R1 Actor and tenant authority missing. Every protected read and effect must derive actor/session and tenant membership server-side; a client-supplied user or business ID cannot grant rights. Guest, business staff/owner and 7even administrator have explicit capabilities. Business A cannot see or change business B, including through reports, notifications, exports, attachments and decision runs. Administrative overrides are scoped, attributable and auditable.

R2 Economic and inventory effects are not durably proven. A reservation consumes capacity once; confirmations and point effects are atomic, idempotent, reconciled and recoverable. Different outcomes such as requested, held, pending business confirmation, confirmed, completed, cancelled, failed, expired and uncertain must be represented explicitly where relevant. A proposed taxonomy is not an approved state machine. Direct business payment and platform reservation states remain distinct. Points issuance/redemption has clear source events and integer amounts; reversals compensate rather than rewrite history.

R3 Multiple sources of truth and nonrepeatable persistence. Use one authoritative database and canonical migrations. Listing, detail, capacity, reservation, reward and decision reads reflect the same committed records. GET must not manufacture domain evidence. Persist histories, permissions, notifications and identities. Seeds are explicit development data, never a silent production fallback.

R4 Interface drift and historical layering. Define one input/output/error contract for each boundary, await asynchronous storage, register routes at startup and exercise the actual API. Retire obsolete generations from runtime and installation. No string-replacement generator should mutate the running source/schema. Sector extension is by a small tested capability interface, not a second shadow engine.

R5 Intelligence claims outrun evidence. Demand output must identify source observations, period, freshness, calculation/model version and limitations. Unknown and insufficient data are valid outputs. Rules can be useful when labelled honestly. Missing evidence cannot become verified; simulated actions cannot become completed effects or actual training outcomes. Goals must affect objective selection. Constraints, owner permissions, inventory and validity override commercial recommendations. Untrusted scenario inputs cannot replace authoritative context for execution.

R6 UI state and API integration are fragile. One generated/shared contract and API client should distinguish loading, empty, error, stale and success states. Every action must call its real backend and display the persisted state after reload. Memoization includes all relevant inputs. Route error containment and accessible controls prevent one screen failure from blanking the product. Every role surface must be exercised in a real browser.

R7 Reproduction and completion are undefined. A clean checkout needs deterministic install, configuration, migration, seed, start and verification commands. Define acceptance criteria before slices; prove invariants with actual DB concurrency/fault tests; review integrations and effects rather than count files. Fresh evidence and unresolved release requirements must accompany completion claims.

PROPOSED MODULE STRATEGY (inference, pending finalized spec)

Keep npm workspaces and React/Vite. Prefer one modular Node API backed by PostgreSQL over preserving seven partially overlapping services. The active need is a coherent engine, not independent scaling boundaries. PostgreSQL already exists in the code and has local test binaries. A dedicated queue, cache, agent runtime, service mesh or new CI framework is not justified by present evidence.

Possible new package responsibilities, all names provisional:
- apps/web: four deliberately designed route shells for public landing/discovery, guest account/reservations/benefits, business operations/demand, and 7even administration. Shared build/runtime is acceptable; product boundaries do not require four deployments. Real mobile app distribution is a separate decision from a responsive web app.
- apps/api: single server composition root, session/authorization, routes, business use cases, persistence adapters and integration adapters. App construction must be importable without automatically listening, to make HTTP tests reliable.
- packages/contracts: canonical API requests/responses, error codes, discriminated state shapes and sector capability contracts. TypeScript could catch the original array/envelope, export and Promise defects early, but runtime boundary validation and actual contract tests are still required. Choose compatible tooling in the finalized implementation plan, not through this read-only audit.
- packages/engine: pure deterministic decision functions, reservation/capacity policies, benefit eligibility/transfer/redemption policy, exact values, observed demand calculations and provenance. Keep business state changes in transactional use cases; a score function must not secretly issue points or reserve a room.
- packages/database: canonical ordered migrations, named repositories and explicit development/test seeds. One configuration family and a scoped test database. No fallback from failed PostgreSQL to SQLite fixture truth.
- packages/ui, if shared components justify it: tokens, accessible controls and role-shell components; avoid a premature generic component library.

Sector extension seam: core Organization, Membership, Listing/Offer, InventoryUnit/Capacity, Reservation, Entitlement, PointsAccount/Postings, Evidence, Observation, DecisionRun and AuditEvent. Hospitality adapters express rooms as occupied date intervals, dining as time slots with covers/table constraints, and experiences as session capacity/participants. Each adapter supplies validation, availability, quote/cancellation rules, fulfilment evidence and permitted benefits. Later sectors must pass the same conformance suite without adding food/hotel-specific conditionals throughout core. Do not flatten every sector into quantity when its capacity semantics differ.

Date intervals, business IANA time zone, cancellation cutoffs, quote expiry, capacity holds and currency precision belong in contracts. Preserve explicit zero values rather than using truthy defaults. NGN quotes use integer minor units or exact decimal types end to end; integer points are a separate unit and must not be formatted as a cash balance. Never imply a fixed cash conversion unless the business model expressly supplies one.

RECEPTION, PWA AND OPERATIONAL SYNC

The reception workspace is a business role surface, with staff check-in/check-out, walk-ins, reservation status, capacity changes and fulfilment actions defined by the final hospitality contract. It is a first-party operational source; each accepted event updates authoritative records and engine observations atomically or through a durable recorded processing state. Automatic sync must be a real exercised flow, not a claim that manually reloading a screen updates intelligence. First-party connector and later PMS adapters share versioned event/snapshot contracts, source identity, business tenant, stable event ID, source revision, event/received timestamps, explicit event type and validation. Unknown event versions/types or incompatible PMS fields go to rejection/review, not guessed translations.

An installable PWA requires actual manifest, icon/start/scope behavior, supported service worker caching and offline/reconnect verification, not just a small-screen stylesheet. Browser/platform support and unsupported install behavior should be stated honestly. Local pending operations must survive tab close/reopen when that is the agreed offline capability, with visible pending/accepted/conflicted/failed states. Choose minimal browser persistence in the plan; do not store full guest or financial records offline by default.

Offline availability is stale. A local queued check-in or booking cannot silently become server-confirmed, consume a reward, or guarantee the last room before reconciliation. Server authorization, current revision, capacity and idempotency are rechecked upon sync; conflicts require clear resolution. Stable event identity survives retries, restart, multiple tabs and reconnect. Do not regenerate IDs on every poll/retry. Prevent duplicate queue processing/claiming and bound retry/backoff. Revoked/expired sessions and tenant changes stop or reject sync safely; logout must clear scoped sensitive local data. Retain diagnostics for rejected events without exposing guest secrets. A rejected old event cannot overwrite a later authoritative cancellation merely because it arrives last.

PMS support in first release means an adapter contract plus tested first-party connector unless an actual third-party adapter is implemented and sandbox-verified. The UI must not display connected/live/automatically synchronized for an unknown PMS. Versioning, source conflict precedence, snapshot-to-event reconciliation and deletion/correction semantics need explicit rules before external adapters are enabled.

INTELLIGENCE ACCEPTANCE BOUNDARY

An honest first engine can combine measured searches, views, availability, reservation conversion and cancellations into explained demand indicators. It must not label seed data as live local demand or promise forecast accuracy without a measured dataset and held-out evaluation. Collect only required events with legitimate scope. Minimum observation counts, time windows, freshness thresholds and recommendation evaluation criteria need values in the final spec. Where data is absent, show that fact rather than synthesizing confident forecasts.

A decision run should record authoritative input revision, source timestamps, requested objective, candidate actions, constraints, chosen recommendation, reasons and policy version. Review/approval is distinct from execution; execution has an effect identifier and read-back verification. A failed or simulated run cannot boost real success/accuracy statistics. Suggested price/promotion actions remain inside business-approved floors, ceilings, capacity, publication and expiry constraints. Runtime automation beyond these agreed effects must have explicit policy; confidence does not grant authority.

OWNERSHIP/TRADE QUESTIONS STILL REQUIRING A PRODUCT RULE

Map ownership to entitlement ownership with traceable origin and redemption history, not ownership of a hotel/property itself. Before implementing trade, decide exactly what can transfer: points, benefit entitlements, booking rights, or combinations; whether business approval is required; whether transfers are gifts or exchanges; and what prevents transfer of consumed, expired, restricted or named-guest benefits. A paid room reservation is not automatically transferable simply because an old food asset was. Do not silently introduce customer cash exchange, monetary value guarantees or custody. These decisions materially alter the state machine and abuse controls.

T12 Direct payment confirmation. Customer claims payment or revisits a redirect URL: reservation is still awaiting valid confirmation. T13 Reservation state machine. Exercise every allowed transition and at least one forbidden transition per state, including cancellation/no-show/partial availability/uncertain confirmation. T14 Points earning. Only eligible verified completion sources grant the agreed integer number of points. Duplicate fulfilment/event/confirmation produces one award. Unconfirmed, failed, cancelled, simulated or self-reported activity does not mint points. Pending versus spendable is explicit. Every award has source, rule version, unit, actor/system identity and matching ledger account postings.
T15 Concurrent points redemption. Seed 100 available points; 20 concurrent 10-point redemptions from independent workers/connections produce exactly 10 successes, zero spendable points and 10 rejections, with no duplicated entitlement. Repeat requests and restart do not add effects. Locked/reserved points count against available points.
T16 Ledger reversal. Cancellation/reversal uses compensating postings referencing original issuance/redemption. Invoke it twice and race it with completion/redemption. Net points agree with policy, no historical deletion, no duplicate compensation, sum of postings balances in the points unit and account projections reconcile to ledger. Decide the policy for reversing already-spent rewards before asserting nonnegative balances in that case.
T17 Benefit ownership/trade. When transfer policy is finalized, test only eligible current owners can transfer, owner changes atomically, and competing transfers/redemptions result in one effect. Restricted/expired/redeemed offers fail. Exchange must persist all agreed legs atomically or fail; pending business approval is not completed ownership. No real-cash effect is inferred.
T18 Exact quote/value. Test integer minor-unit NGN values, explicit taxes/fees/discounts and rounding rules; malformed, negative, zero-where-invalid, oversized and mixed-unit inputs reject.
