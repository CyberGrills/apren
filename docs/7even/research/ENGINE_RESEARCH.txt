7EVEN ENGINE ARCHITECTURE BRIEF
Draft for the parent agent, 16 October 2026. Research and proposal only. No source changes, installation, database provisioning or release verification.

Confirmed direction
The first release covers rooms, dining and experiences in Nigeria. Customers pay businesses directly. Customers earn redeemable points. The Apren ideas of ownership, trade, value, rewards and demand intelligence remain, adapted to hospitality. Landing, customer app, business dashboard, reception workspace and platform admin use the same authoritative engine. More sectors come later. Support both 7even reception software and external PMS integration, starting with 7even's own reception workspace. No external PMS vendor or desktop OS has been selected.

Product interpretation
The transferable idea is time-sensitive capacity becoming discoverable, priced and useful before its service window passes. For hospitality, a room-night, a dining sitting or an experience seat is capacity; a confirmed right to use it is an entitlement. Ownership of an entitlement does not mean ownership of a hotel or a claim on money. Trade means merchant-permitted transfer or exchange of eligible benefits. This interpretation needs explicit product approval before public copy promises transferable bookings or points with a cash value.

What to retain from Apren
- Persistent identity and history: the asset-code resolver, passports, lifecycle records and events express useful traceability concepts.
- A command can update several records atomically: transactions/tradeEngine.js begins a transaction (line 17), locks holdings (lines 24-28), then commits (187). Keep that transactional discipline, rebuild the domain behavior.
- Decisions should have an input snapshot, policy/model version, steps, proposed action and observed outcome: agent/agentKernel.js and agentRunStore.js express this journal structure.
- Keep separate assisted decisions and effects. execution/executionGatewayEngine.js:46 has an explicit simulation branch. Preserve the boundary and make the UI truthful about it.
- Parameterized SQL and the intent of policy evaluation are useful patterns. They are not evidence that current authorization or intelligence is correct.

What to replace
- Food freshness, spoilage, food ownership quantities and food price equations must not be renamed into room logic. Hospitality availability, service dates, cancellation terms, attendance and transfer rights need their own contracts.
- Use one authoritative persistent model. db.js:3-13 opens SQLite, while repositories/assetRepository.js:1-21 writes PostgreSQL. Split reads and writes cannot be a booking engine foundation.
- Replace caller-controlled engine context. agentKernel.js:44-67 takes input freshness/demand/supply/value, then :130 spreads arbitrary input over the context. Authoritative inventory, prices and membership must come from server state.
- Replace authorization by action name. execution/actionAuthorizationEngine.js:1-21 checks only whether SELL_NOW/HOLD/PROMOTE/TRADE is in a list. routes/agentKernelRoutes.js:15-29 forwards user data and mode without a caller/tenant contract.
- Retire overlapping numbered brain generations from the active runtime. The current verifier verifies SIMULATED status, not a fulfilled stay or customer benefit (agent/agentVerifier.js:29-46). Historical scripts stay as history, not migrations.
- Do not carry over wallet funding or cash transfer. transactions/walletTransfer.js:9-12 and :48-64 select/update by user rather than currency. Number arithmetic (:23) and arbitrary funding are unsuitable. 7even does not need a customer cash wallet for the confirmed noncustodial model.

Proposed implementation shape
Use a modular backend and one PostgreSQL authority with a reproducible migration path, shared validated API contracts and a worker for durable follow-up work. Existing Node/React can remain unless another verified requirement rules it out. Start with modules, not a network of small services: identity/access, merchants/venues, catalog, capacity, quotes/offers, reservations/entitlements, direct-payment records, points, exchange, demand/recommendations and audit. Frontends never write storage or maintain their own transactional truth.

Reception and local installation
Deliver an installable reception web/PWA workspace first, backed by the same cloud API and server authority. It is the hotel's front desk for walk-in reservations, arrivals/departures, room/service status, merchant payment confirmation and fulfillment. Dining and experience merchants can use equivalent attendance/fulfillment tools. Staff actions, not a customer's self-declared completion, establish points eligibility. Reception writes immediately update business and customer availability through the common engine. Installation must honestly mean a tested PWA install on supported browsers; a native Windows/macOS package or arbitrary PMS integration remains a separately verified deliverable.

Offline behavior is explicit: cache only the permitted operational minimum, persist a local outgoing queue and show queued edits as PENDING_SYNC. Online server transactions decide booking confirmations. Offline staff cannot promise unbounded shared inventory, issue final points or silently mark platform bookings confirmed. Sync conflicts remain visible for a staff decision. Independent offline-confirmed capacity would require separately partitioned allotments and reconciliation, which are not part of this first proposal.

PMS adapter seam, not an integration claim
Define adapter contracts for capability discovery, property/resource mapping, incremental observations/cursor, availability snapshot, reservation commands/acknowledgments and reconciliation. Each connected property explicitly declares its inventory authority. In the first release, 7even is authoritative; a future external PMS may become authoritative only after its read/write/acknowledgment behavior is tested. Never let two systems blindly overwrite availability or invent an instant external confirmation before the authority acknowledges it.

Every source event carries propertyId, source/deviceId, stable eventId, schemaVersion, source revision/sequence, resource mapping, occurredAt and receivedAt. Persist source cursor and dedupe state durably. Apply events idempotently; stale versions, sequence gaps, deleted mappings and conflicting room states enter review/reconciliation. Compare revisions rather than trusting device clocks. Resume after disconnect/crash from durable acknowledgment, and periodically reconcile a bounded authoritative snapshot to detect missed events.

Provision reception devices with scoped, revocable credentials tied to property and allowed actions; secure transport, rotation, replay controls and explicit audit identity. Do not ship shared secrets in frontend bundles or send full guest records when an inventory/status event suffices. A local agent is justified later only by a selected PMS or device capability that requires it. Then specify OS, secure credential storage, signed installer/update, local queue and support/recovery tests. Browser/PWA storage of guest data needs an agreed retention, logout/device-loss and offline-access policy before caching sensitive records.

Sector extension seam
Shared contracts: tenant/business; location; published offering; resource/capacity; service window; quote; reservation; entitlement; points journal; demand event; recommendation; audit event. A sector module supplies required attributes, capacity measurement, eligibility rules, fulfillment states and presentation. Build three explicit hospitality modules now. Rooms allocate room-type units for each local service date in [check-in, check-out); dining allocates a stated number of covers in a configured sitting; experiences allocate seats in an occurrence. Dining must state its capacity model and cannot imply a full table-layout optimizer. Future sectors implement the same contracts without adding food/room fields to the core. Do not build a generic workflow language before a second sector establishes the need.

Non-negotiable engine properties
1. Capacity: active holds plus confirmed allocations never exceed saleable capacity for any relevant service unit/window. Out-of-service capacity is excluded. Confirmation, expiry and cancellation compete under the same database transaction/locks. Cancellation and expiry release an allocation at most once. Inventory changes cannot silently evict existing guests.
2. Dates: store a venue time zone, local service dates/times and absolute event timestamps. Count room nights using calendar dates, not elapsed milliseconds. Define check-in/out, dining buffers and experience cutoffs explicitly. Reject zero/negative duration, past windows and invalid party sizes.
3. Quotes: server-created immutable price/terms snapshots include NGN integer minor units, units, fees/taxes, discount, total, policy version and expiry. Changing an offer does not alter an accepted quote. A quote alone does not hold capacity. Display estimates as estimates.
4. Lifecycle: model requested, held, awaiting merchant payment, confirmed, fulfilled, cancelled, expired and rejected outcomes explicitly; maintain payment/refund state separately. Only valid transitions execute. Never equate an external checkout redirect or uploaded receipt with paid. A late payment after hold expiry enters review/refund resolution; it cannot overbook capacity.
5. Direct payments: persist merchant, expected amount/currency, reservation, external reference, observed status, verifier and time. The customer pays the merchant through a verified merchant payment link or instructions. Confirm by trusted merchant action or a configured provider protocol, with an attributable audit record. 7even records the payment state; it cannot claim it settled funds it does not handle.
6. Points: use exact integers and an append-only journal, never a mutable balance as the only truth. Bind every earn/redeem/reverse to a unique business event and policy version. Reserve points during checkout/exchange, atomically commit or release once, prohibit overspending and duplicate issuance. Corrections use compensating entries. A conservative proposal earns points only after confirmed fulfillment; cancellation, fraud and refunds have explicit reversal rules.
7. Ownership and trade: an entitlement has one current owner, original transaction, merchant transfer policy, status, expiry and transfer history. Trade acceptance locks both sides, rechecks eligibility/versions, moves rights and points atomically, and invalidates the old owner's right. Fulfilled, cancelled, expired or restricted benefits cannot transfer. Default unconfigured transfer rules to unavailable. Cash resale is outside the direct-payment engine until a settlement/dispute contract is approved.
8. Authorization: a server-verified actor and membership determine the tenant/property scope. Every command and read checks both role and resource ownership. Customers see their reservations; staff see allowed venues; owners manage only their businesses; platform admin privileges are explicit and audited. Role names in a browser or a supplied tenantId are not authority. Apply the same rules to jobs, exports, uploads, caches and recommendation records.
9. Durability: each mutation has a caller-scoped idempotency key bound to its payload hash; reuse with different content fails. Persist the mutation, audit record and outbox event together. Workers claim durable jobs with bounded retries/timeouts and idempotent consumers. Provider uncertainty stays pending/review rather than triggering blind retries. No distributed exactly-once claim.
10. Demand intelligence: ingest source-labelled, timestamped search, availability, quote, booking, cancellation and fulfillment facts. Deduplicate events and retain coverage/freshness. A recommendation returns the input revision, reason, constraints, expiry and policy/model version. Hard eligibility/capacity/price-floor rules run before ranking. Missing data yields insufficient-data, not invented confidence. Recommendations use the ordinary authorized commands when approved and are revalidated before effect.

Bounded interfaces to specify before coding
- browseOfferings(filters) returns published, permitted listing fields and explicit availability freshness.
- quoteOffering(offeringId, window, party/quantity) returns server-priced quoteId, exact total, terms snapshot and expiresAt.
- placeHold(quoteId, idempotencyKey) returns allocationId, expiresAt and version, or a typed capacity/price/policy conflict.
- syncReceptionEvents(propertyId, sourceId, events, cursor) returns durable acknowledgments and per-event applied/duplicate/conflict outcomes; it never treats queued local edits as confirmed server effects.
- createReservation(holdId, customerDetails) binds a guest to the allocation; payment instructions and pending state are truthful.
- recordMerchantPayment(reservationId, evidence/reference, expectedVersion) is a privileged, attributable confirmation command, not a customer balance-credit endpoint.
- transitionReservation(id, action, expectedVersion) handles confirmation, fulfillment and cancellation with capacity/points effects in one transaction.
- issue/redeem/reversePoints(sourceEventId, policyVersion, idempotencyKey) exposes journal entries and available/reserved points.
- propose/acceptEntitlementExchange(entitlementIds, recipient/offerId, expectedVersions, idempotencyKey) rechecks merchant restrictions and ownership atomically.
- evaluateDemand(scope, asOf, policyVersion) returns evidence-backed recommendations, never direct unrestricted database mutations.
All mutations carry requestId and authenticated actor context. Responses distinguish validation, authentication, authorization, not-found, stale-version, capacity-conflict and review-required outcomes. Sensitive fields are excluded from public payloads.

Tenant and data boundaries
Business is the tenant; a venue/property is a subordinate permission scope; hospitality category is a capability, not a tenant. Include tenant scope on business-owned records and enforce tenant-consistent relationships. Public catalog rows are deliberate projections. Cross-business demand reports need aggregation and a disclosure policy; do not expose competitor bookings, guest identities or exact private economics. PostgreSQL row security may add defense in depth, but the runtime database role must not bypass it and it does not replace endpoint authorization. Admin support access and exports need their own audited permissions.

Two remaining critical policy decisions
A. Points: who funds them, whether they work across merchants, earn/redemption rates, expiry, minimums/caps and who bears refunds after points are spent. Store these as versioned merchant/network policy; do not invent a universal conversion or reward liability.
B. Direct payment: initial merchant-confirmed manual records or a specific provider with merchant-owned accounts; hold duration and late-payment/refund obligations. Recommendation: a complete manual merchant-confirmed workflow first, clearly labelled and audited, with the provider seam ready. If user expects instant payment confirmation, provider/account access is a prerequisite.
Operational configuration also needs approved cancellation/no-show/transfer rules, merchant onboarding checks, points fraud limits, notification sender and deployment target. These can be concrete settings rather than blocking the independent engine contracts.

Verification criteria
- Fresh database migration + seed + start + one real API-backed customer journey visible in business and admin screens. Restart preserves it. No local-only confirmation screen.
- Run separate DB connections/processes against one remaining room, dining cover/party capacity and experience seat: concurrent requests never oversell; multi-night allocation rolls back as a whole. Race confirmation against expiry/cancellation.
- Verify walk-in versus customer booking races, reception offline edits, device restart, duplicate/reordered events, stale revisions, missing cursor gaps, revoked device credentials and authoritative snapshot reconciliation. Pending offline operations must never render as final customer confirmations or issue final points.
- Replay the same mutation and points event ten times; one effect. Same key/different payload conflicts. Kill worker before/after commit and delivery; restart recovers without duplicate issuance, release or notifications.
- Attempt cross-customer, cross-business and cross-venue reads/mutations, exports, run IDs and direct APIs. Fail without leaking sensitive records. Test staff access revocation during active sessions.
- Verify exact NGN totals and point sums, maximum values, zero/negative/malformed inputs, reserved points, concurrent redemptions, refund/reversal policy and trade ownership. Check final records, not only HTTP codes.
- Test direct-payment pending, rejection, duplicate confirmation, late payment, wrong amount/reference, merchant revocation and refund review. If a provider is added, verify sandbox signatures, replay protection, duplicates, out-of-order events and timeout-after-payment recovery against provider records.
- Evaluate demand rules on labelled scenarios and time-held-out data before predicting commercial gains. A deterministic baseline must beat or justify itself against a simple historical comparison. Synthetic/sample data stays labelled. Simulated outcomes never count as actual fulfillment or revenue.
- Browser acceptance on landing/customer/business/admin: all roles, links, forms, empty/loading/error states, date ranges, mobile/tablet/desktop, keyboard, screen reader semantics, reduced motion and no hidden fake success. Independent review examines consequential authorization/points/trade behavior before production; no autonomous deploy.

Primary sources consulted, and scope
PostgreSQL transaction isolation: https://www.postgresql.org/docs/current/transaction-iso.html . Its default read-committed behavior does not alone establish multi-row booking invariants. Serialization failures require whole-transaction retry; implementation must choose and test its concurrency strategy.
PostgreSQL explicit locks: https://www.postgresql.org/docs/current/explicit-locking.html . Row locks coordinate conflicting updates. Acquire multiple resources in consistent order, keep transactions short and handle deadlock/serialization failures with bounded retries.
PostgreSQL row security: https://www.postgresql.org/docs/current/ddl-rowsecurity.html . Policies can restrict reads/writes; owners and BYPASSRLS roles have bypass behavior that matters to runtime design.
Stripe idempotent requests: https://docs.stripe.com/api/idempotent_requests . A provider-specific example of binding retry keys to request parameters; this is not a Stripe selection or proof of availability for this product.
Stripe webhooks: https://docs.stripe.com/webhooks . The provider requires raw-payload signature checks and documents duplicate and unordered delivery. Apply the selected provider's own protocol if an integration is later chosen.
